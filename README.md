# 緒言
---
 近年、ゲノム解析の飛躍的な発展に伴い作物や畜産、養殖など幅広い分野でゲノム情報を活用した研究が展開されている。とくに一塩基多型（single nucleotide polymorphism, SNP）のハイスループットジェノタイピングは多くの生物で大規模な多型解析を可能とし、家系管理や、ゲノム選抜育種（Genomic selection, GS）法の普及とその導入による選抜育種の飛躍的な効率化に貢献している<sup>1)</sup>。また、SNP多型解析や<sup>2)-4)</sup>、ゲノム選抜育種で育種価予測を行うためのBioinformatics用の解析ツールも数多く開発されている<sup>5)-8)</sup>。一方で、これらの解析ツールの多くはLinux OS上での利用を前提として開発されており、コマンドライン操作が基本となっている。このことは、特に初心者にとって導入の障壁となり、普及を妨げる要因の一つである。さらに、ソフトウェアのインストールにおいては、バージョンや依存関係の違いにより解析環境との不一致が生じることがあり、適切な環境構築が困難となる場合がある。加えて、研究及び実際の育種現場での運用においては、一連の作業を効率的かつ再現性高く行うことが特に重要になるが、パソコンの更新などがあった場合、ソフトウェアをインストールする過程で、関連するライブラリやソフトウェアの依存関係が崩れたり、プロジェクトの途中でバージョンが変わったりするなどが原因で、再現性を担保できないような状況も発生する。バイオインフォマティクス初心者にとっては、「どこに何をインストールしたか」「使用したバージョンは何か」といった管理作業自体が大きな負担となる。そのような課題の解決には、複数のツールとその依存関係を適切に管理・統合できる解析環境の構築が有効である。

 このような背景を踏まえ、本研究ではBioinformatics解析の導入、実行、管理を容易にするため、Docker<sup>9)</sup>を利用したゲノム選抜育種向けの解析環境をの構築を提案するした。具体的には、Windows11上でLinux OS (Ubuntu)を実行できるWindows Subsystem for Linux 2（WSL2）をインストールし、シーケンスリードの参照配列へのマッピングとジェノタイピング、育種価予測までを網羅するDockerイメージを作成した。Dockerは、アプリケーションの実行に必要なツール群とその依存関係を1つのコンテナとしてパッケージ化するプラットフォームであり、環境の再現性と可搬性を確保できるという大きな利点を有している。本研究で作成したDockerコンテナ環境は、Linら<sup>10)</sup>で使用されたソフトウェアを再現可能にしている。このコンテナは固定のものではなく、ユーザー自身が研究目的に応じて使用するツールや手法を柔軟に編集・拡張できる汎用性を保持する。記載されたコマンドはWSL2環境に準拠した形式となっているが、他のOS環境で実行する場合でも各OSに適したコマンドやファイルパス表記に置き換えれば実行可能である。ただし、ここで紹介しているWSL2、Dockerなどの各種ソフトウェアのインストールはネットワーク接続を前提としている。

# 目的
---
- Dockerを使用し簡便かつ利便性の高い解析環境を構築し遺伝育種の普及性を向上させること
- 作成した解析環境の動作確認ならびにDocker環境とDockerを介さないローカル環境との間で処理性能を比較し、ゲノム選抜育種の解析パイプラインとしての有用性を評価すること

## 2-2 動作確認
　ここでは２台のPCを使用して、同一の手順でDockerイメージから解析環境としてのコンテナを起動し、Linら<sup>10)</sup> にある解析を再解析し、解析結果の出力が行われるかを検証した。具体的には、Linら<sup>10)</sup>の方法に従って、トラフグの鰓腔壁に寄生したHeterobothrium okamotoiの虫体数（Heterobothrium count, HC）とトラフグの標準体長（standard length, SL）を表現型として育種価のゲノム予測を12種類のモデルを使って行い、10分割の交差検証で求めた予測能（predictive ability）、すなわち、得られたゲノム予測育種価と表現型との間の相関の強さをピアソンの積率相関係数（r）、で評価した。交差検証でデータを分割する際に用いるランダムシードは固定し、２つのPC間で同じ分割が実施されるようにした。ただし、ランダムシードの記載がなかったLinら<sup>10)</sup>とは異なる分割となった。使用したPCのスペックを表１にまとめた。
## 2-3 処理性能の比較
Dockerを利用した解析環境の処理性能を評価するため、上記のPC2を使用して、トラフグ（_Takifugu rubripes_）1個体から新たに得たGRAS-Di<sup>18）</sup>データを使用し、リードのトリミングからGATKのHaplotypeCallerでGVCFファイルを生成するまでの解析処理時間を計測した。比較のため、Dockerで扱うソフトウェアをPC2に直接インストールしたLocal環境でも解析を行い、処理時間を計った。その際、ひとつのタスクを複数のスレッドで同時に処理するMulti-threadingと、ひとつのタスクを複数に分割したうえでスレッドごとに作業を割り当てて並行処理するScatteringを行った。Multi-threadingでは処理全体で使用できるメモリを24GB均等に設定し、Scatteringではメモリをスレッド間で均等にした。
# 結果
---
## 結果3-1　再現性の確認
　12のモデルでそれぞれ評価した予測能は、Linら<sup>10)</sup>の結果とくらべほぼ同じ結果が得られた（表２、３）。同一の結果とならなかった原因としては、交差検証で異なるランダムシードが使われていたためであると考えられた。一方で、ランダムシードが等しいPC1とPC2では同じ結果が得られたことから、解析環境の再現性が支持された。

## 結果3-2　処理性能の比較
　Multi-threadingで実行した際の処理時間は、Docker環境とローカルの環境でどちらも4-8 スレッドの方が16 スレッドよりも早く、11-13分であった（図１）。16 スレッドで処理時間が遅くなったのはメモリの競合によるCPU効率の低下や、データの読み込みと書き込み時にボトルネックが発生したことが理由として考えられた。
　一方、Scatteringでは8-16分割のときで4-5分程度となり、Multi-threadingの場合と比べ処理時間は半分以下に短縮された（図２）。しかし、Docker環境ではLocal環境と比べ20秒程度長かった。ゲノム予測で1000個体を解析する場合には、Docker環境では80時間、Local環境では75時間となり、Dockerでは5時間遅くなることとなるが、解析開始からどちらも3日で終わる計算となり、運用上では許容範囲の差といえた。

# 考察
---
　今回の結果から、作成したDockerイメージは正常に解析を実行でき、かつ、異なるPCにおいても結果の再現性を保持できることが確認された。これにより、本研究で構築したパイプラインは、水産養殖の現場においても利用可能であると言えた。なお、Dockerfile中のWSL2の導入部分をスキップすれば、UbuntsuなどのLinux環境に各種の解析ソフトをインストールできる。また、Docker環境は一般にLocal環境と同等の性能を示すとされるが、処理内容や並列化手法に依存して性能差が生じる。本研究においても、scatteringで実行した際に、Docker環境ではLocal環境に比べて処理時間が長かった。ゲノム選抜育種で用いられる規模（1,000個体）ではリードのトリミングからHaplotypeCallerによるGVCFファイルの生成までのステップで5時間程度の差が生じることが予想された。しかし、どちらの環境でも3日程度で終わることから、実用上問題のない差範囲であると言えた。また、scattering時の分割数や各分割処理に割り当てるthread数やメモリ上限を最適化する等で、さらに短縮化できる可能性もある。以上のことから、本研究で構築した解析環境は再現性と実用性の両立を可能とするものであり、導入や運用の障壁を低減するジェノタイピングパイプラインとして有効であると考えられる。
